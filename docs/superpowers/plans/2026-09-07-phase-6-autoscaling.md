# Phase 6 Autoscaling implementation plan

**Goal:** Make the Native Variant's parallelism respond to load instead of
sitting at 6, and demonstrate Karpenter's provisioning loop against fake nodes,
with four Drills that each produce a real transcript.

**Architecture:** The Flink Job Autoscaler runs inside the Flink Kubernetes
Operator, reads busy time and backlog from the job's own REST API, and applies a
new parallelism in place through `PUT /jobs/:jobid/resource-requirements`. The
JobMaster re-declares its slot requirement, and in `mode: native` the
ResourceManager creates TaskManager pods itself. Pod count is never set; it is
`ceil(slots needed / slots per TaskManager)`. Separately, Karpenter with the kwok
provider watches for unschedulable pods generated by a Decoy Workload and creates
fake nodes, which touches no Flink object.

**Tech Stack:** Flink 2.2.0, Flink Kubernetes Operator 1.15.0, Karpenter with the
kwok provider, `kind`, Strimzi, MinIO, ArgoCD, Gradle 9.7.0.

**Spec:** [Autoscaling design](../specs/2026-09-07-autoscaling-design.md)

**Knowledge:** [Phase 6 knowledge](../../knowledge/phase-6-autoscaling.md), for
how any of this works. This plan does not re-explain mechanism.

## Global constraints

Every task's requirements implicitly include this section.

- **`:pipeline` stays frozen.** No change may alter the job graph, the operators,
  or their semantics. This is the Phase 5 constraint as amended on 2026-09-07 and
  it is **not** lifted.
- **`:generator` may change.** Phase 5's "no file under `apps/` changes" is lifted
  for `apps/generator/` only, per spec 5.4. No Flink operator reads it.
- **`apps/pipeline/conf/config.yaml` does not exist and is not recreated.** It
  was deleted in commit `b0705e0` when the configuration moved into
  `spec.flinkConfiguration`, per spec 7.6. The Phase 5 constraint forbidding its
  edit is satisfied vacuously. Every Phase 6 key goes in the manifest alone.
- **`apps/gradlew -p apps :pipeline:test` must stay green** after any edit.
- **`spec.flinkConfiguration` is `map[string]string`.** Every number and boolean
  is quoted. Durations are accepted unquoted.
- **Push to `master`, not `phase-2`.** `root.yaml` uses `targetRevision: HEAD`,
  which resolves to the default branch. Work committed elsewhere deploys nothing
  and reports no error anywhere. Use `git push origin phase-2:master`.
- **`job.autoscaler.vertex.max-parallelism: "6"` is a safety mechanism, not a
  tuning knob.** Every kind node advertises the whole 23.5 GiB host, so the
  scheduler will never report `Pending` for memory. Raising this without redoing
  the arithmetic in spec 4.3 will swap the machine.
- **Flink pods never tolerate the kwok taint.** A TaskManager on a kwok node
  reports `1/1 Running` with no JVM behind it, and the job hangs waiting for slots
  that never register.

## Task 1: Generator, remove the 1000/sec ceiling

**Files:** Modify `apps/generator/src/main/java/lab/personalization/generator/SkewedEventStream.java`,
the `start` method only.

**Goal.** Make the Load Ramp able to exceed 1000 Clicks/sec.

**The concept.** The current code schedules one tick per Click and floors the
period at 1 millisecond:

```java
long periodMillis = Math.max(1, Math.round(1000.0 / eventsPerSecond));
```

`--click-rate=5000` therefore yields 1000/sec and reports nothing. The fix
inverts the relationship: **fix the period, vary the batch.**

**The failure mode to watch for.** The 1 ms floor goes away; the silent
fall-behind does not. `scheduleAtFixedRate` never runs a tick concurrently with
itself, so if one batch takes longer than the period, ticks simply lag. That is
why Step 3 measures rather than trusts.

- [x] **Step 1: Rewrite `start`.**

Skeleton, not a finished method:

```java
public void start(double eventsPerSecond) {
    final long periodMillis = 10;
    final int perTick = (int) Math.max(1, Math.round(eventsPerSecond * periodMillis / 1000.0));
    ticker.scheduleAtFixedRate(() -> { for (int i = 0; i < perTick; i++) tick(); },
                               0, periodMillis, TimeUnit.MILLISECONDS);
}
```

Three constraints, each with a reason:

1. **The ticker stays single-threaded.** The comment at `SkewedEventStream.java:50`
   records that event time ordering depends on ticks firing sequentially. Batching
   preserves that. A thread pool would not.
2. **`Instant.now()` stays inside `tick()`,** which it already is. Do not hoist it
   into the loop body, or 50 Clicks share one timestamp and the watermark
   arithmetic changes.
3. **Leave `tick()` itself alone.** Only `start` changes.

- [x] **Step 2: Build.**

```bash
apps/gradlew -p apps :generator:build
```

- [x] **Step 3: Measure the achieved rate. This is the gate.**

Run the generator against a high rate and sample the topic, exactly as in Task 0
Step 4:

```bash
apps/gradlew -p apps :generator:run --args="--click-rate=800 --click-max-skew-seconds=1"
```

In another shell, sample `clickstream` offsets ten seconds apart and divide.

**Expected: near 800/sec, not 1000, and not 200.** If it lands well below the
request, the batch is taking longer than 10 ms and you have found the
fall-behind mode. Record the number you actually achieve, because spec 8.2's
arithmetic and Task 2's Session length both depend on it.

Note the `--click-max-skew-seconds=1`. `SkewedPublisher` schedules each send up
to that far into the future, so at 800/sec with the 2 s default there are ~1600
pending scheduled tasks at all times.

**Done when** you have a measured rate from topic offsets, written down.

## Task 2: Generator, key cardinality

**Files:**
- Modify `apps/generator/src/main/java/lab/personalization/generator/factory/Catalog.java`
- Modify `apps/generator/src/main/java/lab/personalization/generator/GeneratorConfig.java`
- Modify `apps/generator/src/main/java/lab/personalization/generator/Generator.java`, lines 37-38

**Goal.** 2,000 Shoppers and 200 Products, both CLI-configurable.

**The concept.** Ten keys hash into at most ten of the 120 key groups. At
parallelism 6 about 5 of 6 subtasks receive work; at 8, about 5.9. Scaling buys
almost nothing, the autoscaler's ineffective-scaling detection notices, and
further scale-ups are blocked. The demonstration fails while appearing to run.

**Why 2,000 and not 10,000.** A Browsing Session only builds up while a Shopper's
Clicks arrive closer together than the 6 s gap:

```
E[Clicks per Session] = e^(sessionGap × clickRate ÷ shopperCount)
```

At 800 Clicks/sec: 10 Shoppers gives Sessions that **never close** and emit
nothing. 10,000 gives Sessions of 1.6 Clicks, so `SessionAggregator` aggregates
nothing. 2,000 gives about 11, which is a Session.

**Why 200 Products and not more.** Product count is the denominator of Task 4's
pressure lever, `comparisons per Click ≈ productChangeRate × 4s ÷ productCount`.
Raising it removes the lever.

**The failure mode to watch for.** Fixing the wrong list. The pipeline has its
own `recommendationCatalogue` of P1..P10, and it must stay that way.
`DeterministicMockClient.answerFor` hashes any `candidateProductId` into it, so
it is an answer set, not a key set. Do not touch `:pipeline`.

- [x] **Step 1: Turn `Catalog`'s constants into a factory.**

```java
public static List<String> ids(String prefix, int count) {
    return IntStream.rangeClosed(1, count)
            .mapToObj(i -> prefix + "-" + i)
            .toList();
}
```

Note the existing ids are `shopper-1` and `P1`, two different shapes. Keep both
shapes so nothing downstream is surprised, or change both deliberately and say so.

- [x] **Step 2: Add two options to `GeneratorConfig`.**

Two record components, two defaults, two `case` arms in the existing `switch`:

```java
case "shopper-count" -> shopperCount = Integer.parseInt(value);
case "product-count" -> productCount = Integer.parseInt(value);
```

Defaults `2000` and `200`. The record's canonical constructor is package-private
and its component list is positional, so adding components means updating the
`new GeneratorConfig(...)` call at the end of `parse`.

- [x] **Step 3: Build the lists in `Generator`.**

`Generator.java:37-38` already constructs the factories with `Catalog.SHOPPER_IDS`
and `Catalog.PRODUCT_IDS`. Replace those two references with calls to the new

## Task 4: Drill E, dry run under a Load Ramp

**Files:** Create `docs/runbooks/phase-6-drill-e-dry-run.md`

**Goal.** Confirm the autoscaler's recommendation is sane before letting it act.

**The concept.** `job.autoscaler.enabled` and `job.autoscaler.scaling.enabled` are
two switches. The first runs the whole algorithm and publishes
`RECOMMENDED_PARALLELISM`. The second applies it. Running with the first alone is
a dry run, and given that four of five blockers produce a plausible but wrong
recommendation, it is the only cheap way to tell a working autoscaler from a
broken one.

**The failure mode to watch for.** Nothing happening for the first three minutes
is **correct**. `job.autoscaler.metrics.window: 3m` means it will not decide
before it has three minutes of history. The most common "the autoscaler is
broken" report is someone watching for ninety seconds.

- [x] **Step 1: Start the Load Ramp.**

```bash
apps/gradlew -p apps :generator:run \
  --args="--click-rate=800 --product-change-rate=400 --click-max-skew-seconds=1"
```

`--product-change-rate=400` is the pressure lever. The interval join's cost per
Click is `productChangeRate × 4s ÷ productCount`, so 400 over 200 Products gives
8 comparisons per Click against today's 0.4. That is pure CPU in the operator's
own task thread, which is exactly what `busyTimeMsPerSecond` measures.

- [x] **Step 2: Wait out the metrics window.** Three minutes, plus the
  stabilization interval if the job restarted recently. Do not intervene.

- [x] **Step 3: Read the recommendation per vertex.**

The autoscaler exports metrics named
`[prefix].Autoscaler.[jobVertexID].[ScalingMetric].Current`. Read them from the
operator's metrics endpoint, or from the operator log, which reports its scaling
summary per vertex.

```bash
kubectl -n flink-operator logs deploy/flink-kubernetes-operator -c flink-kubernetes-operator \
  --since=10m | grep -i 'scaling\|parallelism\|recommend'
```

Map each `jobVertexID` back to a name with the job graph command from Task 0.

- [x] **Step 4: The gate, and it is specific.**

`RECOMMENDED_PARALLELISM` must rise on **the three Click-consuming vertices**: the
session window, the CEP operator, and the interval join. Those are the only
vertices carrying full Click rate, and all three sit after a `keyBy`, so none is
partition-bound.

**If it rises on the sink, or on `Co-Process-Broadcast` instead, stop.** Something
in Task 1, 2 or 3 did not actually take effect. Those vertices see the signal
rate, which is roughly a twentieth of the Click rate, and they should not be the
bottleneck.

Also check `LOAD` and `TRUE_PROCESSING_RATE` on the session window. If
`TRUE_PROCESSING_RATE` is implausibly low, the print sinks are still chained and
Task 3 Step 3 did not land.

> **Not needed. 2026-09-08.** `--product-change-rate=400` moved the

## Task 6: Drill G, scale down

**Files:** Create `docs/runbooks/phase-6-drill-g-scale-down.md`

**Goal.** Watch parallelism and pod count fall again. This is the half most
demonstrations skip.

**The failure mode to watch for, and it is the whole point of this task.**
Parallelism falls first. Pods follow later, and sometimes not at all.

Two independent reasons:

1. **A pod is deleted only when it holds zero subtasks.** A half-used
   TaskManager is kept, wasting a slot.
   `jobmanager.adaptive-scheduler.prefer-minimal-taskmanagers` decides whether
   the scheduler packs subtasks onto fewer TaskManagers, which frees whole pods,
   or spreads them, which frees none.
2. **An idle TaskManager is held for a timeout** before the ResourceManager
   releases it, so a freed pod can be reused rather than recreated seconds later.

Lingering pods immediately after a scale-down are expected and are not a failure.

- [x] **Step 1: Read the two settings from the live configuration.** Do not assume
  defaults.

> **Corrected on 2026-09-08. This step cannot be run as written.**
> `/jobmanager/config` returns only the keys that were explicitly set, 62 on this
> cluster. A default that was never overridden is indistinguishable from a key
> that does not exist, and `job.autoscaler.*` keys never reach the JobManager at
> all. Take defaults from the operator's configuration reference and take the
> packing behaviour from what the pods do.
>
> **Two settings this task never named, and they govern the whole Drill:**
> `job.autoscaler.scale-down.interval` defaults to **1 hour**, so Step 3's
> "3 minutes plus stabilization plus cooldown" is wrong by roughly an hour. And
> `job.autoscaler.scale-down.max-factor` defaults to **0.6**, so a vertex cannot
> drop below 60% of its parallelism in one decision. Shrinking happens in steps.
> See [the Drill G runbook](../../runbooks/phase-6-drill-g-scale-down.md).

```bash
curl -s localhost:30011/jobmanager/config | python3 -m json.tool \
  | grep -i 'taskmanager-timeout\|taskmanager-release\|prefer-minimal'
```

Write both values into the runbook before you start, so the expected result is
derived rather than guessed.

- [x] **Step 2: Stop the Load Ramp.** Leave the job running and idle.

- [x] **Step 3: Wait out the window.** Same 3 minutes, plus stabilization, plus
  cooldown.

- [x] **Step 4: Confirm parallelism fell, from the rescale history**, not from pod
  counts. Another `triggerCause: UPDATE_REQUIREMENT` record, with
  `postRescaleParallelism` **below** `preRescaleParallelism`.

- [x] **Step 5: Then watch the pods**, for at least the idle timeout you read in
  Step 1.

```bash
kubectl -n personalization-blue get pods -w
```

If pods do not fall to one, check whether the subtasks spread rather than packed.
That is a legitimate outcome and the runbook should say which happened and why.

- [x] **Step 6: Gap check** with `recommendation-snapshot.sh`, as in Task 5.

## Task 7: Karpenter, install, NodePool, Decoy Workload

**Files:**
- Create `manifests/karpenter/nodepool.yaml`
- Create `manifests/karpenter/decoy.yaml`
- Add a `karpenter` stage to `scripts/bootstrap.sh`

**Goal.** A real Karpenter controller, fake nodes, and a workload that cannot be
placed on the real ones.

**The concept.** Karpenter watches for pods the scheduler could not place. No
unschedulable pod means no provisioning, ever. kwok creates `Node` objects with
nothing behind them, so nothing real may land there.

**The failure mode to watch for, and the phase plan gets this wrong.** A
toleration is **permission, not attraction.** A Decoy pod that merely tolerates
the taint schedules onto a real worker immediately, Karpenter sees nothing
pending, and the Drill appears to run while proving nothing. Resource pressure
cannot rescue it either: every node advertises 23.5 GiB that does not exist.

**Two mechanisms, two jobs:**

| Field | Job |
|---|---|
| Decoy `nodeSelector: node-role=decoy` | **Makes it unschedulable.** No real worker has this label |
| Decoy `tolerations` for `workload=flink:NoSchedule` | Lets it land once Karpenter creates a node |
| Flink pods: neither | Can never reach a kwok node |

- [x] **Step 1: Install, outside ArgoCD, and record why.**

> **Expanded on 2026-09-08, after probing upstream at `02caf5a` (2026-09-02).**
>
> **There is no published Helm chart and no published controller image.** The
> chart files exist, inside the repo at `kwok/charts`, so Helm is pointed at a
> directory on disk instead of a URL. `kwok/charts/values.yaml` ships
> `controller.image.repository: ""`, an empty string, which is upstream telling
> you to supply your own image.
>
> **Two things share the name.** *kwok* is the node simulator that makes a fake
> `Node` behave like a node. *Karpenter with the kwok provider* is the autoscaler
> that decides to create nodes, using kwok as its pretend cloud. Both are needed,
> in that order.
>
> **The order, and why each step must precede the next:**
>
> ```
> Decoy pod unschedulable
>         │  needs
>         ▼
> Karpenter controller ──needs──> container image (nobody publishes one)
>         │  needs                └─ needs the Go source
>         ├──> CRDs (NodePool, NodeClaim, KWOKNodeClass)
>         │  needs
>         ▼
> kwok running ── makes a fake Node actually behave like a node
>         │  needs
>         ▼
> the source repo ── holds the chart, the kwok installer, and the code
> ```
>
> 1. **Clone `kubernetes-sigs/karpenter`.** The chart, the kwok installer and the
>    Go source all live here and nowhere else.
> 2. **`./hack/install-kwok.sh`.** Pure `curl` and `kubectl apply`, pinned at kwok
>    `v0.8.0`. Without kwok, Karpenter creates nodes that never go `Ready`, and
>    the Decoy stays `Pending` looking exactly like Karpenter failing.
> 3. **Build the controller image and `kind load` it.** Skip this and the
>    Deployment sits in `ImagePullBackOff`.
> 4. **`kubectl apply -f kwok/charts/crds`.** The controller watches custom
>    resources, so the API server must know the types first. The chart is
>    installed with `--skip-crds`, so if you do not apply them, nobody does.
> 5. **`helm upgrade --install karpenter kwok/charts -n kube-system --skip-crds`.**
>    The Deployment, ServiceAccount and RBAC. Needs 3 and 4.
> 6. **Then Steps 2 and 3 below:** NodePool first, Decoy second.
>
> **The host has neither `go` nor `make`.** Build the image in Docker rather than
> installing a Go toolchain, matching `scripts/build-image.sh`'s build-then-`kind
> load` pattern. `go.mod` requires **Go 1.26.6**. Nothing then touches the
> machine, and deleting the image undoes it.
>
> **Facts read out of the upstream Makefile, not guessed:**
>
> - **`KARPENTER_NAMESPACE=kube-system`** (`Makefile:3`). This step's "record the
>   namespace" can be answered now.
> - **kwok is pinned to `v0.8.0`** in `hack/install-kwok.sh`. Pin it in
>   `bootstrap.sh` too, as its `phase0` stage pins cert-manager and ArgoCD.
> - **`--skip-crds` is required**, with the CRDs applied separately.
> - **Feature gates are required values**, interpolated unconditionally at
>   `kwok/charts/templates/deployment.yaml:104`. Upstream `HELM_OPTS` sets
>   `settings.featureGates.nodeRepair`, `capacityBuffer` and `staticCapacity`

> - **Upstream requests 1 CPU / 1Gi and limits 2 CPU / 2Gi for the controller.**
>   Task 0 recorded host headroom at 2.5 GiB and Drill F showed this host
>   saturating. Consider halving these and record why in the script.

The kwok provider lives in `kubernetes-sigs/karpenter` under `kwok/` and installs

toolchain, and there is no published Helm chart.

cert-manager and ArgoCD itself in Phase 0. Capture the commands in

reproducible.

the pipeline's exit code, not the script's.

- [x] **Step 2: Write the NodePool and the KWOKNodeClass.**

```yaml
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: decoy
spec:
  template:
    metadata:
      labels:
        node-role: decoy            # what the Decoy selects on
    spec:
      taints:
        - key: workload
          value: flink
          effect: NoSchedule        # what keeps TaskManagers off
      requirements:
        - key: kubernetes.io/arch
          operator: In
          values: ["amd64"]
        - key: kubernetes.io/os
          operator: In
          values: ["linux"]
      nodeClassRef:
        group: karpenter.kwok.sh
        kind: KWOKNodeClass
        name: default
  limits:
    cpu: "20"
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 10s
---
apiVersion: karpenter.kwok.sh/v1alpha1
kind: KWOKNodeClass
metadata:
  name: default
```

`limits.cpu: "20"` is a hard ceiling in the same spirit as
`vertex.max-parallelism`. Nothing else bounds provisioning, and a runaway Decoy
Workload would otherwise create kwok nodes without limit. Twenty is roughly four
fake nodes.

`consolidateAfter: 10s` makes Drill H's scale-down observable in seconds.

- [x] **Step 3: Write the Decoy Workload.**

A `Deployment` of `registry.k8s.io/pause`, `replicas: 0` to start, carrying
**both** the `nodeSelector` and the toleration from the table above.

`pause` is chosen because it does nothing. A pod that does nothing does not care
that it is never really executed, which matters because a kwok node runs nothing.
